# Plan for WMHA-0032

## Goal and scope

Decide by experiment whether the `last_update_success` half of the run event publication guard in
`custom_components/windmill/event.py:56` earns its place, then pin the resulting behavior with a
test that fails when it is removed.

Non-goals per ticket: no change to event types, attributes or the retention model; no persisted
"published" marker; no edits to WMHA-0022/0023 in `tickets/done/`.

## Experiment 1 — is the half load-bearing today?

Mutation: replace the guard with `if snapshot is self._published:` and run the suite.

Result 2026-08-03: **392 passed**. No test discriminates the half. Reproduces the ticket's claim.

## Experiment 2 — enumerate the notification sources (pinned HA 2026.7.4)

`DataUpdateCoordinator` notifies listeners from exactly three places:

- `_async_refresh`, after `self.data = await self._async_update_data()` (success), or with `data`
  untouched when the refresh raised — `self.data` is assigned on line 371 of the class source and
  nowhere else on the failure path;
- `async_set_update_error`;
- `async_set_updated_data` (assigns `self.data` on line 546).

This integration calls neither `async_set_update_error` nor `async_set_updated_data` for the run
coordinator (`grep` over `custom_components/`: no hits). A repeated failure returns early
(`if not self.last_update_success and not previous_update_success: return`), so a failure streak
notifies once.

Conclusion: a listener notification can carry a snapshot that is **unpublished and not fresh** in
exactly one situation — the snapshot produced by the refresh during config-entry setup, while the
entity's catch-up delivery is still waiting for `EVENT_HOMEASSISTANT_STARTED`. For every snapshot
the entity has already published, `snapshot is self._published` alone prevents republication,
because a failed refresh cannot replace the object.

## Decision

**Remove the `last_update_success` half and replace it with an explicit "Home Assistant has
started" gate.**

Rationale:

- Republication (the WMHA-0022 outcome) is fully carried by the identity check; the half adds
  nothing there.
- In the one case where the half does act — the failed poll before `EVENT_HOMEASSISTANT_STARTED` —
  it does not merely suppress a duplicate. It suppresses the *only* delivery of a real completion,
  and the catch-up at `EVENT_HOMEASSISTANT_STARTED` hits the same guard because
  `last_update_success` is still `False`. That is the permanent loss window of known limitation 2.
- Dropping the half without replacement would publish the pending snapshot during bootstrap, where
  automations have not attached their triggers yet (see
  `docs/blog/2026-08-02-events-fired-during-bootstrap-reach-no-automation.md`). The deferral is the
  part worth keeping; `last_update_success` was the wrong condition to express it.

The new condition is a `_started` flag set by the existing `async_at_started` callback, so the
entity publishes when and only when the catch-up moment has arrived, regardless of whether the poll
in between succeeded.

## Failure modes

- A snapshot published during bootstrap would reach no automation → the gate defers instead.
- Publishing at `EVENT_HOMEASSISTANT_STARTED` while the coordinator is in a failure streak marks
  the entity unavailable in the same cycle; the event still reaches the bus, which is what an
  automation trigger consumes. Recorded as a residual observation if the tests show it.

## Plan changes

- The first mutation check of the replacement guard passed (395 tests), so the plan's mutation
