# Plan for WMHA-0005

## Current state verified

- `custom_components/windmill/api.py` parses the public coarse health response into
  `WindmillHealthStatus` but only validates and discards `/api/health/detailed`.
- `custom_components/windmill/coordinator.py` owns one capability coordinator with a six-hour
  interval. No health polling exists and no entity platform is registered anywhere.
- WMHA-0004 stores feature opt-ins in `entry.options`: `instance_health` defaults to enabled and
  `detailed_health` defaults to disabled because it is administrative.
- ADR-0001 keeps the capability matrix authoritative: an optional denial must disable only the
  affected feature.
- `docs/research/windmill-api-contract.md` records the bounded detailed-health model
  (`checks.database`, nullable `checks.workers`, nullable `checks.queue`, `checks.readiness`) and
  warns that granular-scoped tokens fail before the handler in v1.775.2.

## Design decisions

1. **A second coordinator, not a second client.** `WindmillHealthCoordinator` polls once per minute
   and produces one immutable snapshot for every health entity, so entity count never changes the
   request count.
2. **Coarse health is the contract; detailed health is additive.** The coarse call decides
   availability of the update. A failing or denied detailed call only empties the detailed part of
   the snapshot, and `401` still raises `ConfigEntryAuthFailed` because it invalidates the token.
3. **Feature gating happens once, at setup.** Health entities exist only when the user enabled
   `instance_health` and the capability probe reported `available`. Queue diagnostics additionally
   require `detailed_health` plus its capability. Later capability churn changes entity state, not
   the entity set, so entities never appear and disappear on every refresh.
4. **Bounded projection only.** The detailed model keeps database health, alive workers and the two
   queue counts. Pool internals, worker versions, group names, readiness details and any other
   upstream field are discarded in the client.
5. **One service device per config entry.** Identifiers use the entry ID, the configuration URL is
   the credential-free base URL, and entity names come from translation keys.

## Entity model

| Platform | Entity | Source | Category |
| --- | --- | --- | --- |
| `sensor` | Health | coarse `status` as the bounded enum `healthy`/`degraded`/`unhealthy`; Home Assistant renders an unreadable value as `unavailable` instead of a synthetic option | none |
| `sensor` | Alive workers | coarse `workers_alive` | diagnostic |
| `sensor` | Pending jobs | detailed `checks.queue.pending_jobs` | diagnostic |
| `sensor` | Running jobs | detailed `checks.queue.running_jobs` | diagnostic |
| `binary_sensor` | Database | coarse `database_healthy`, connectivity | diagnostic |

Status mapping for the health sensor:

| Observation | Entity result |
| --- | --- |
| Coarse `status` is `healthy`, `degraded` or `unhealthy` | the same bounded enum state |
| Connection, timeout, rate-limit, server or contract failure | `unavailable` until the next successful refresh |
| `401` on either health call | `unavailable` plus a reauthentication flow |
| Detailed health denied, missing or malformed | coarse entities keep working; queue entities become `unavailable` |
| Health capability unsupported or the feature disabled | no health entity is created at all |

## Failure modes and rollback

- Detailed health is denied or missing — the snapshot keeps coarse data, queue entities become
  unavailable and the entry stays loaded.
- Coarse health fails temporarily — the coordinator reports the failure once, entities become
  unavailable and recover on the next successful refresh.
- The token is revoked — `401` raises `ConfigEntryAuthFailed`, which starts the WMHA-0004
  reauthentication flow.
- Health is unsupported by an old deployment — no health coordinator is created and no entity is
  registered, while the rest of the entry keeps working.
- Rollback is one ticket commit. Entity unique IDs are derived from the config-entry ID, so no
  registry migration is introduced.

## Security and privacy review

- Credentials: coarse health stays public and unauthenticated; detailed health uses the shared
  bearer header. No entity state, attribute, System Health value or log line contains the token.
- Sensitive payloads: the detailed parser keeps five bounded values and discards pool internals,
  worker identities, versions, group names and every unknown field.
- Permissions: no administrative permission is required for the default entity set.
- Network exposure: two bounded GETs per minute at most, and System Health only checks the public
  version endpoint.
