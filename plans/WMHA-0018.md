# Plan for WMHA-0018

## Current state verified

- `custom_components/windmill/event.py:36` loops over `coordinator.data.new_events`, calls
  `_trigger_event()` per completion and writes the entity state exactly once, through
  `super()._handle_coordinator_update()`.
- The installed `homeassistant/components/event/__init__.py:158` confirms the mechanism: the `@final`
  `_trigger_event` only assigns `__last_event_triggered`, `__last_event_type` and
  `__last_event_attributes`. The event becomes observable only when the state is written, so
  consecutive triggers overwrite each other and only the last one survives.
- `homeassistant/core.py:2414` drops a state write only when state *and* attributes are unchanged.
  Two completions always differ in `job_id`, so one write per completion is always observable even
  when both writes land inside the same millisecond and share the `state` timestamp string. The
  standard state trigger uses `match_all` when neither `to` nor `from` is configured
  (`homeassistant/components/homeassistant/triggers/state.py:124`), so attribute-only changes still
  reach automations.
- The coordinator already sorts completions ascending by `(completed_at, id)` in
  `coordinator.py:373` and only emits events after the first observation, so ordering and the
  historical-replay suppression need no change.
- `event.py:52` starts `registry.async_forget(...)` through `hass.async_create_task`. That task is
  owned by nothing: an entry unload does not wait for it, and one task per tracked completion means
  several concurrent `Store.async_save` calls built from independently mutated dictionaries.
- `StartedJobRegistry` (`coordinator.py:559`) has no mutual exclusion at all; `async_track` from
  `services.py:94` can interleave with a forget in the same way.

## Failure modes and rollback

- Two completions inside the same millisecond share the `state` timestamp string. The attributes
  differ, so the write is never dropped and `match_all` state triggers still fire. Accepted: the
  timestamp is owned by the `@final` `_trigger_event`, and the ticket forbids subclassing it.
- Automations that relied on the collapsed behavior now fire once per completion. That is the
  intended correction and is recorded in the ticket's residual risks.
- The extra write after the loop is a no-op whenever nothing changed, and remains necessary for the
  availability transitions the existing rate-limit test covers.
- Rollback is one ticket commit; no storage schema, entity registry entry or option changes.

## Plan changes

  mutating method outside the lock would have made the invariant conditional rather than structural.

  single identifier, so the batching is additive.
