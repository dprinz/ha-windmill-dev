## Design decisions

1. **One unified listing per refresh.** `/api/w/{workspace}/jobs/list` with the documented
   `has_null_parent=true` and `is_flow_step=false` filters returns queued and completed top-level
   jobs together, so running counts, last-run timestamps and completion events come from the same
   bounded page walk.
2. **Structural discrimination.** A row carrying `success` is a completed job and a row carrying
   `running` is a queued job. The union discriminator name is not relied upon, so a rename upstream
   degrades to a protocol error rather than to a wrong state.
3. **No entity per job.** The workspace gets four aggregate sensors and exactly one event entity
   whose event types are `success`, `failure` and `canceled`.
4. **Watermark plus recent-identifier retention.** A Home Assistant `Store` keeps the newest
   observed completion timestamp, the last 200 completed job identifiers and the monotonic
   last-success and last-failure timestamps. A job fires an event only when it is newer than the
   watermark and not already in the identifier list, which also prevents duplicates across
   reloads and restarts.
5. **The first observation never replays history.** When no stored state exists, the first refresh
   only records the watermark, identifiers and timestamps and fires no event.
6. **Bounded page walk.** At most three pages of 100 rows per refresh; the walk stops early on a
   short page or as soon as a page is entirely at or below the watermark.
7. **Scope selection is deferred.** Scoping to selected runnables or to Home Assistant-started jobs
   needs the runnable selection of WMHA-0008 and the started-job registry of WMHA-0009 and
   WMHA-0010. Neither exists yet, so this ticket observes all visible top-level jobs and the scope
   selector becomes the new backlog ticket WMHA-0017 instead of a half-wired option.

## Entity model

| Entity | Source | Category |
| --- | --- | --- |
| Workspace running jobs | queued rows with `running` true, within the observed window | none |
| Workspace queued jobs | queued rows with `running` false | none |
| Last successful run | monotonic newest `completed_at` of a successful job | none |
| Last failed run | monotonic newest `completed_at` of a failed job | none |
| Run event | one event entity with `success`, `failure` and `canceled` event types | none |

| Observation | Result |
| --- | --- |
| Job completes successfully after the watermark | one `success` event with job identifier, kind, path and duration |
| Job fails or is canceled | one `failure` or `canceled` event |
| Job already seen, or older than the watermark | no event |
| Skipped flow-internal job | ignored entirely |
| Listing fails, is rate limited or is denied | every run entity becomes unavailable |
| `401` during a refresh | unavailable plus a reauthentication flow |
| `runs` capability unavailable or the feature disabled | no run entity is created |

## Failure modes and rollback

- Windmill inserts jobs while the walk is running — the watermark advances only to the newest
  completion actually observed, and the identifier list absorbs the overlap.
- A job completes with no `completed_at` — it is counted but never fires an event, because an
  event without a timestamp cannot be deduplicated safely.
- Rate limiting — the refresh fails, entities become unavailable and the next interval retries.
- Stored state is corrupt or from a future version — it is discarded and the next refresh behaves
  like a first observation, which is safe because it replays nothing.
- Rollback is one ticket commit. The store is additive; removing it only loses duplicate
  suppression across a restart.

## Security and privacy review

- Credentials: the listing uses the shared bearer header only.
- Sensitive payloads: the parser keeps the identifier, state, kind, path, creation and completion
  timestamps and duration. `args`, `result`, `logs`, `flow_status`, `email`, `permissioned_as`,
  `canceled_reason`, `labels` and `tag` are discarded in the client and never reach entity state,
  event data or the store.
- Permissions: only `jobs:read`-level access is required, and a denial disables this feature alone.
- Network exposure: at most three bounded GETs per minute.

## Open questions

- Whether a very busy workspace needs a longer page walk cannot be answered without a live
  deployment; the current bound is documented and conservative.
- Event replay guarantees across a Home Assistant restart depend on the stored retention window of
  200 identifiers, which is a policy choice rather than an upstream guarantee.
