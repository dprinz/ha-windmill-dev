# Plan for WMHA-0020

## Current state verified

- `custom_components/windmill/__init__.py` has `async_setup`, `async_setup_entry` and
  `async_unload_entry`, but no `async_remove_entry`.
- The two store keys are written inline at `__init__.py:136` (`windmill.runs.<entry_id>`) and
  `__init__.py:166` (`windmill.jobs.<entry_id>`); nothing else knows them.
- `Store.async_remove` in the pinned Home Assistant version invalidates the manager entry, cancels
  the delayed and final-write listeners and unlinks the file under `suppress(FileNotFoundError)`, so
  a never-written store is safe to remove. A different `OSError` can still surface.

## Proposed changes

| File or component | Change | Acceptance criterion |
| --- | --- | --- |
| `coordinator.py` | Add `async_run_store`, `async_job_store` and the `ENTRY_STORES` tuple of factories that owns both keys | Store keys live in one place |
| `__init__.py` | Build both stores through the factories | Same keys, no behavior change on setup |
| `__init__.py` | Add `async_remove_entry` that removes every store in `ENTRY_STORES` and never raises | Removal deletes both stores and cannot block entry removal |
| `tests/test_init.py` | Regression tests for removal, for unload/reload keeping state, for an unwritten store and for a second entry staying untouched | All acceptance criteria |

## Sequence

1. Introduce the factories and re-point setup.
2. Add `async_remove_entry`.
3. Add the regression tests; confirm they fail without `async_remove_entry`.
4. Run the ticket's validation commands.

## Failure modes and rollback

- An `OSError` while unlinking — logged at warning level; entry removal still completes, and the
  orphaned file is the same outcome as today. Rollback is a single-file revert of `__init__.py`.
- Removing the wrong store — prevented by keying every factory on `entry_id` and by the regression
  test that removes one of two configured entries.

## Security and privacy review

- Credentials: none; the stores hold identifiers, kinds, paths and timestamps only.
- Sensitive payloads: this ticket only deletes stored data; nothing new is written or logged. The
  warning log names neither the store path nor its contents.
- Permissions: unchanged.
- Network exposure: none; removal is local file work.

## Open questions

- Stores orphaned by add-and-remove cycles before this change are not cleaned retroactively.
  Decision: acceptable, because a retroactive sweep would have to guess which `windmill.*` store
  files belong to entries that no longer exist. Recorded as a residual risk for the `WMHA-0013`
  documentation instead.
