# Plan for WMHA-0010

## Current state verified

- WMHA-0009 starts runnables and returns the job identifier, but nothing keeps it.
- WMHA-0007 already observes completions and owns the watermark retention model, so lifecycle
  events must reuse it instead of adding a second event source.
- `docs/research/windmill-api-contract.md` records `POST /api/w/{workspace}/jobs_u/queue/cancel/{id}`
  with a JSON reason, requires `jobs:write` plus per-job authorization, and states that only
  identifiers from the bounded Home Assistant-started registry may be cancelled.

## Design decisions

1. **The registry only ever contains what Home Assistant started.** The run action records the
   returned identifier; nothing else can enter the registry, so arbitrary workspace jobs stay
   uncancellable through this integration.
2. **Bounded by size and age.** At most 50 jobs and at most 24 hours, enforced on every read and
   write, persisted per config entry.
3. **Metadata only.** A tracked job keeps the identifier, kind, path and start time. Arguments,
   results and logs are never persisted.
4. **Cancellation is explicit and predictable.** An untracked identifier is refused locally. A
   `404` or `409` means the job already finished or cannot be cancelled, which removes it from the
   registry and reports a validation error. Authentication, permission and transport failures stay
   distinct.
5. **Completion reuses the existing event entity.** Every event now reports whether Home Assistant
   started the job, and a tracked job is forgotten as soon as its completion is observed, which
   keeps the registry small without a second polling loop.

## Defect found and fixed

The WMHA-0007 run coordinator inferred "first observation" from an empty watermark. On a workspace
that was idle during the first poll, the second poll was still treated as the first one, so the
first real completion never fired an event. Retention state now carries an explicit `initialized`
flag. The fix belongs to this ticket because its acceptance criteria depend on lifecycle events
actually firing for Home Assistant-started jobs. A regression test covers the empty-first-poll case.

## Failure modes and rollback

- Home Assistant restarts while a job runs — the registry is restored from disk, expired entries are
  dropped and the completion still fires exactly once.
- The registry file is corrupt — unreadable rows are discarded and tracking simply starts over.
- A job completes between the cancel decision and the request — Windmill answers `404` or `409` and
  the job is forgotten with a clear message.
- Rollback is one ticket commit; removing the registry only removes cancellation.

## Security and privacy review

- Credentials: cancellation uses the shared bearer header and the fixed reason string.
- Sensitive payloads: nothing beyond identifier, kind, path and start time is stored.
- Permissions: cancellation additionally needs `jobs:write` and per-job authorization; a denial is
  reported without changing the registry.
- Network exposure: one bounded POST per cancellation.
