# Plan for WMHA-0003

## Current state verified

- WMHA-0001 and WMHA-0002 are accepted in commits `603dc3a` and `dca7322`.
- The existing asynchronous client centralizes setup URL handling, bearer authentication,
  timeouts and bounded bodies, but only models `/api/version` and workspace `whoami`.
- Runtime data currently contains the client and identity only; there is no shared coordinator or
  explicit capability result for later platforms.
- A read-only check against the user-provided test instance on 2026-08-02 confirmed `200` for
  `/api/version` and `/api/health/status?force=false`, and `401` without credentials for detailed
  health, worker listing and workspace job listing. No token was read or sent and no remote state
  was changed.
- The accepted contract requires safe GET probes. Execution and cancellation cannot be proven
  without a target-specific write, so setup must not perform those operations.

## Capability semantics

Each capability has one of the accepted five states: `available`, `unauthorized`, `unsupported`,
`temporarily_unavailable` or `not_applicable`. A bounded reason enum records whether the result
came from a successful probe, permission denial, missing endpoint, temporary failure, unexpected
contract or missing target context.

| Capability | Safe setup evidence | Successful setup state |
| --- | --- | --- |
| General health | Public `GET /api/health/status?force=false` | `available` for valid `200` or `503` health models |
| Detailed health | Authenticated `GET /api/health/detailed` | `available` for valid `200` or `503`; `403` is capability-local |
| Workers | Bounded `GET /api/workers/list?page=1&per_page=1&ping_since=300` | `available` only for a valid list response |
| Runs | Bounded top-level `GET /api/w/{workspace}/jobs/list` | `available` only for a valid list response |
| Script discovery | Bounded script-list GET | Independent read-only result; never copied into execution status |
| Flow discovery | Bounded flow-list GET | Independent read-only result; never copied into execution status |
| Script execution | No safe target-free write probe | Always `not_applicable` until explicit runnable selection; write permission remains operation-time evidence |
| Flow execution | No safe target-free write probe | Always `not_applicable` until explicit runnable selection; write permission remains operation-time evidence |
| Cancellation | No safe target-free write probe | Always `not_applicable` until a Home Assistant-started eligible job exists |
| Update visibility | Bounded `GET /api/uptodate` contract probe | `available` means endpoint support only; Cloud/self-host eligibility remains a later product decision |

`401` from any authenticated probe invalidates authentication. `403` and `404` affect only the
optional capability. Connection, timeout, rate-limit and server failures become temporary states;
malformed success responses become unsupported/incompatible states. No server error body enters
the model.

## Dependency decision

- No dependency is added. Production continues to use Home Assistant's bundled `aiohttp` session
  and coordinator framework; the independent client depends only on `aiohttp` and the standard
  library.

## Failure modes and rollback

- Optional endpoint returns `403`/`404` — record a local capability state and keep the entry loaded.
- Token becomes invalid — preserve `WindmillAuthenticationError` and let the coordinator translate
  it to `ConfigEntryAuthFailed`; reauthentication UI remains owned by WMHA-0004.
- Probe transport/server failure — retain a temporary capability state rather than failing unrelated
  features or logging an upstream body.
- A write capability is falsely inferred from read access — prohibited by the contextual
  `not_applicable` state; WMHA-0009/0010 must establish target-specific authorization at operation
  time.
- Coordinator shutdown regresses — public unload/reload tests execute the registered real shutdown callback and assert runtime removal. Interval scheduling begins only when later platforms attach listeners.
- Rollback is one ticket commit; no config-entry schema migration is introduced.

## Security and privacy review

- Only constant safe GET paths and bounded pagination/query values are probed.
- The token remains in the `Authorization` header only; the public health/version probes omit it.
- Error bodies, health details, worker rows, job rows and runnable rows are validated only for shape
  during discovery and are not retained.
- Probe fan-out is fixed and bounded; setup never executes or cancels a job.
- The live check used no credential and performed no remote mutation.

## Open questions

- Restricted-token `whoami` and capability UX were not instance-tested because no disposable token
  was available without reading or mutating existing credentials; WMHA-0004 owns that onboarding
  gate before presenting permissions to users.
- Detailed-health variants with granular/admin tokens were not instance-tested; WMHA-0005 owns
  that gate before consuming detailed health. Cloud health/worker behavior remains WMHA-0005/0006.
- Reliable Cloud versus self-host classification has no verified safe endpoint; WMHA-0004/0011
  must resolve deployment eligibility before exposing an update entity.
- Exact restricted-token hash/version execution and cancellation enforcement still requires a
  disposable target-specific test in WMHA-0009/0010.
