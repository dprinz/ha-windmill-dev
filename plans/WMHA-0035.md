## Failure modes and rollback

- **`default_branch` empty in the event payload.** Then `git fetch origin ""` fails and the
  job stops with a non-zero exit before creating a release. That is fail-closed: no bad
  artifact escapes. Rollback is a one-line revert to a literal `master`.
- **Default branch renamed again.** The event payload follows the rename, so the workflow
  keeps working; the three push triggers would need updating, which is the same one-line
  edit and is visible immediately because CI stops running on pushes.
- **Publishing the wrong commit.** Mitigated by re-tagging on `master` HEAD only after the
  workflow fix is merged there, and by `build_release.py` refusing a tag whose version does
  not match `manifest.json`.
- Full rollback for this change is `git revert` of a single commit touching only workflow
  YAML.

## Security and privacy review

- Credentials: none added or read. `GH_TOKEN` remains `secrets.GITHUB_TOKEN`, scoped to the
  release job.
- Sensitive payloads: none. The change moves a branch name.
- Permissions: unchanged — workflow level `contents: read`, release job `contents: write`,
  `validate-hacs` keeps `permissions: {}`.
- Injection surface: `github.event.repository.default_branch` is a repository setting, not
  user-controlled content, but it is still passed through an `env:` entry and referenced as
  `"$DEFAULT_BRANCH"` rather than interpolated into the shell command, consistent with how
  the file already handles `github.ref_name`.
- Network exposure: none. Release triggers stay tag-only, so a pull request from a fork
  still cannot reach `contents: write`.
