# Plan for WMHA-0023

## Current state verified

- `async_setup_entry` (`__init__.py:144`) runs `run_coordinator.async_config_entry_first_refresh()`
  before `async_forward_entry_setups` (`__init__.py:194`), so the setup snapshot with its
  `new_events` is never delivered to `WindmillRunEventEntity`: `CoordinatorEntity.async_added_to_hass`
  registers the listener without invoking `_handle_coordinator_update`.
- The completion is still recorded in the retention state (`coordinator.py:448`), which is
  persisted immediately (`coordinator.py:423`), so no later poll reports it again. The event is
  lost, not deferred.
- `WindmillRunSnapshot` is a fresh frozen dataclass per successful poll, and the `WMHA-0022` guard
  (`event.py:41`) already publishes only for a fresh snapshot after a successful poll. The setup
  snapshot is exactly such a fresh, never-published observation, so routing it through the same
  handler needs no new publication logic.
- Automations attach their triggers only at `EVENT_HOMEASSISTANT_STARTED` when Home Assistant is
  starting (`homeassistant/components/automation/__init__.py`, `_async_enable`); a state change
  fired during bootstrap reaches no automation. `homeassistant.helpers.start.async_at_started`
  runs a callback at that event, or immediately when Home Assistant is already running (reload).

## Design decision (open assumption from the ticket)

Carry the pending events in the snapshot until the event entity consumes them; do **not** defer
the first refresh. Deferring the refresh until after platform setup would leave every run entity
without data at add time and would change the `ConfigEntryNotReady` failure semantics of the
setup refresh. Carrying the events keeps one publication path (`_handle_coordinator_update`),
keeps the retention state the single source of truth for "seen", and the "one snapshot per poll"
contract stays intact: the snapshot is published at most once, by identity.

Publication timing: `WindmillRunEventEntity.async_added_to_hass` schedules one catch-up delivery
through `async_at_started`, so a cold start cannot fire before automations are listening, while a
reload (Home Assistant already running) publishes immediately. The catch-up call goes through
`_handle_coordinator_update`, so freshness, success and identity guards apply unchanged; a first
ever setup finds an empty `new_events` tuple and publishes nothing, so no history is replayed.

## Failure modes and rollback

- Over-publication: a completion fires twice across reload, failed poll and recovery — guarded by
  the updated failed-poll test and the unchanged dedup and ordering tests.
- Under-publication on cold start: the catch-up waits for `EVENT_HOMEASSISTANT_STARTED`, which
  automation setup precedes, so no publication can precede trigger attachment.
- Rollback is a single-file revert of `event.py`.
