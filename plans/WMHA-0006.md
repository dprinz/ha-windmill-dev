# Plan for WMHA-0006

## Current state verified

- `custom_components/windmill/api.py` probes `/api/workers/list` for the `workers` capability but
  has no worker model and no worker read operation.
- WMHA-0005 established the entity pattern: one snapshot coordinator per data family, one service
  device per entry, feature gating at setup and bounded parsing in the client.
- WMHA-0004 stores feature opt-ins in `entry.options`; `worker_details` already exists and defaults
  to disabled.
- The pinned worker handler returns `WorkerPing` rows with `worker`, `worker_instance`,
  `last_ping`, `started_at`, `ip`, `jobs_executed`, `last_job_id`, `last_job_workspace_id`,
  `custom_tags`, `worker_group`, `wm_version`, occupancy rates and memory fields
  ([worker handler at v1.775.2](https://github.com/windmill-labs/windmill/blob/v1.775.2/backend/windmill-api-workers/src/lib.rs),
  verified 2026-08-02). `ip`, both last-job fields and `custom_tags` are on the sensitive-data
  denylist.
- `docs/research/windmill-api-contract.md` records that `/api/configs/list_worker_groups` needs
  `configs:read`, that queue aggregate endpoints additionally need the DevOps role, and that
  `HIDE_WORKERS_FOR_NON_ADMINS` can make the worker list legitimately empty.

## Design decisions

1. **Worker identity is the instance, not the worker name.** Windmill worker names carry a
   per-process suffix, so entities keyed by them would churn the registry on every restart. Group
   entities use the group name and opt-in per-worker entities use `worker_instance`, both of which
   survive a worker restart.
2. **The group and instance sets are fixed at setup.** `/api/configs/list_worker_groups` supplies
   configured groups; if it is denied or missing, the first worker snapshot supplies them. Worker
   instances come from the same first snapshot. A group or instance that later reports no worker
   keeps its entity and drops to zero instead of disappearing, and a newly added group or host
   appears after the next reload.
3. **No new capability field.** The existing `workers` capability already proves the worker list.
   Group listing degrades locally at setup, so the ADR-0001 matrix stays unchanged and the periodic
   capability refresh gains no extra request.
4. **Queue pressure stays with detailed health.** `/api/workers/queue_counts` and its running
   variant are DevOps-gated and keyed by tag rather than by worker group, so they cannot express
   per-group pressure honestly. WMHA-0005 already exposes bounded pending and running job counts
   from detailed health, and this ticket does not duplicate them per tag. This is a deliberate
   scope decision recorded in the ticket rather than a silent omission.
5. **Two opt-ins, both disabled by default.** `worker_groups` covers group entities and
   `worker_details` covers per-instance entities. Both are administrative monitoring, so both stay
   off until the user enables them.
6. **Bounded pagination in the adapter.** The client returns one validated page; the coordinator
   walks at most five pages of 100 rows and stops early on a short page.

## Entity model

| Entity | Source | Category | Gate |
| --- | --- | --- | --- |
| `{group} workers` | alive workers whose `worker_group` matches | diagnostic | `worker_groups` |
| `{group} worker versions` | distinct `wm_version` values in the group | diagnostic | `worker_groups` |
| `Workers on {instance}` | alive worker processes with that `worker_instance` | diagnostic | `worker_details` |

| Observation | Entity result |
| --- | --- |
| Group has alive workers | count and distinct version count |
| Group configured but idle, or hidden by `HIDE_WORKERS_FOR_NON_ADMINS` | zero, not unavailable |
| Worker list fails or is denied at refresh | every worker entity becomes unavailable |
| `401` during a refresh | unavailable plus a reauthentication flow |
| `workers` capability unavailable or both opt-ins disabled | no worker entity is created |

## Failure modes and rollback

- Worker listing is denied — no worker coordinator is created and the rest of the entry keeps
  working.
- Group listing is denied — groups come from the observed workers instead.
- A worker restarts with a new name — the instance and group entities keep their identity because
  neither uses the worker name.
- More alive workers exist than the bounded page walk covers — counts are a documented lower bound
  and a debug message records that the walk stopped at the limit.
- Rollback is one ticket commit; entity unique IDs derive from the entry ID plus stable names, so
  no registry migration is introduced.

## Security and privacy review

- Credentials: worker reads use the shared bearer header only.
- Sensitive payloads: the parser keeps worker name, instance, group and version. `ip`,
  `last_job_id`, `last_job_workspace_id`, `custom_tags`, occupancy rates and memory values are
  discarded in the client and never reach entity state or attributes.
- Permissions: no DevOps or superadmin role is required; a denial disables only this feature.
- Network exposure: at most five bounded GETs every two minutes, plus one group listing at setup.

## Open questions

- Cloud tenant behavior for the instance-global worker list is still untested against a live
  deployment; the gate stays recorded in `docs/research/windmill-api-contract.md`.
- Whether `HIDE_WORKERS_FOR_NON_ADMINS` is set cannot be detected through the API, so an empty
  worker list is reported as zero rather than as a permission problem.
