# Plan for WMHA-0004

## Current state verified

- `custom_components/windmill/config_flow.py` implements one `user` step that collects base URL,
  workspace and token, validates through `WindmillClient.async_validate` and compares normalized
  entry data for duplicates. There is no reauth, reconfigure or options flow.
- `custom_components/windmill/__init__.py` registers `entry.add_update_listener` and reloads the
  entry on every config-entry update. Home Assistant 2026.7.4 forbids combining an update listener
  with `OptionsFlowWithReload`, so the lifecycle owner has to be chosen explicitly.
- `custom_components/windmill/api.py` exposes a workspace-bound `WindmillClient`. No client
  operation exists that works before a workspace is known, so a separate connection step needs an
  instance-scoped transport surface.
- `docs/research/windmill-api-contract.md` records `GET /api/workspaces/list` as a bearer-
  authenticated JSON array of visible workspaces and assigns restricted-token `whoami` verification
  to this ticket.
- ADR-0001 requires the five-state capability matrix to stay authoritative at runtime; onboarding
  may present it but must not convert an optional denial into setup failure.
- The test environment is Home Assistant 2026.7.4 with `_get_reauth_entry`, `_get_reconfigure_entry`,
  `async_update_reload_and_abort`, `_abort_if_unique_id_mismatch` and `OptionsFlowWithReload`
  available.

## Design decisions

1. **Identity stays data-derived.** Duplicate detection keeps comparing the canonical base URL plus
   workspace across existing entries instead of introducing a unique ID. Entries created by
   WMHA-0002 have `unique_id is None`, so adopting a unique ID now would silently split identity
   between old and new entries and would break `_abort_if_unique_id_mismatch` for legacy entries.
2. **Instance versus workspace transport split.** `WindmillInstanceClient` owns the base URL, the
   bearer header, timeouts, bounded reads and every instance-scoped call (`/api/version`,
   `/api/health/status`, `/api/uptodate`, `/api/workspaces/list`). `WindmillClient` extends it with
   workspace identity, `whoami` and capability discovery. This keeps the connection step honest
   without inventing a placeholder workspace.
3. **Workspace listing is optional.** `401` remains an authentication failure. `403`, `404` and a
   malformed list degrade to manual workspace entry, because restricted tokens without
   `workspaces:read` must still be able to finish onboarding.
4. **Options own feature selection.** Immutable identity (base URL, workspace) and the credential
   stay in `entry.data`; feature toggles live in `entry.options`. The options flow uses
   `OptionsFlowWithReload`, and `__init__.py` drops the update listener because Home Assistant
   forbids using both.
5. **Feature defaults are conservative.** Administrative and high-cardinality features default to
   disabled. Only instance health and run observation default to enabled, and only when their
   capability probe succeeded.
6. **The feature schema is capability-independent.** Every toggle is always offered; only the
   default value depends on the capability snapshot. A `temporarily_unavailable` probe therefore
   never silently deletes a user's stored selection, and runtime capability gating stays the single
   authority for entity creation in later tickets.

| Lifecycle flow | Behavior |
| --- | --- |
| `reauth` | Only the token may change; base URL and workspace come from the existing entry and are re-validated before `async_update_reload_and_abort` |
| `reconfigure` | Base URL, workspace and an optional replacement token; empty token keeps the stored credential; identity collisions with other entries abort |
| `options` | Feature toggles only; reload is automatic through `OptionsFlowWithReload` |

## Failure modes and rollback

- Workspace listing is unauthorized or missing — fall back to manual workspace entry instead of
  failing onboarding.
- The token is valid for the instance but not for the chosen workspace — `whoami` fails at the
  workspace step and the user stays in the assistant with a field-level error.
- Reauth is started for an entry whose instance moved — the flow re-validates the stored identity
  and reports the failure rather than rewriting identity silently.
- Reconfigure targets an identity already owned by another entry — abort with
  `already_configured` and leave both entries untouched.
- Removing the update listener regresses reload behavior — public lifecycle tests reload the entry
  explicitly and assert one additional connect and capability refresh.
- Rollback is one ticket commit; no config-entry version bump or data migration is introduced,
  because existing entries keep their `data` shape and simply have empty `options`.

## Security and privacy review

- Credentials: the token stays in config-entry data and the `Authorization` header. It is never a
  form default, never a description placeholder, never logged and never part of the entry title.
- Sensitive payloads: workspace listing retains only bounded `id` and `name` strings; every other
  field is discarded. Capability presentation uses status tokens only, never upstream error bodies.
- Permissions: onboarding requires only `users:read`-level access; missing `workspaces:read` or any
  administrative permission downgrades a feature default instead of blocking setup.
- Network exposure: only bounded safe GET requests run during onboarding, reauth and reconfigure.
  No job is started or cancelled.
