# Plan for WMHA-0011

## Current state verified

- The capability matrix already probes `/api/uptodate`, but ADR-0001 states explicitly that
  `update_visibility=available` proves only the endpoint contract and never deployment eligibility.
- `docs/research/windmill-api-contract.md` records the plain-text contract (`yes` or
  `Update: <installed> -> <latest>`), that the upstream handler performs an outbound GitHub call
  with a ten-second deadline, and that Windmill Cloud is `not_applicable` because it is managed.
- WMHA-0005 established the coordinator and entity pattern, and the `update_entity` option from
  WMHA-0004 already exists and defaults to disabled.

## Design decisions

1. **Eligibility is a conjunction, not a guess.** The entity exists only when the user enabled
   `update_entity`, the capability probe succeeded, and the base URL is not a managed Cloud host.
   The explicit opt-in is the user's deployment declaration; the host check is a safety net so a
   Cloud tenant cannot accidentally receive a meaningless update entity.
2. **Failures are non-fatal by construction.** The update check depends on GitHub availability, so
   setup uses a plain refresh instead of the first-refresh helper. A failure leaves the entry loaded
   and the entity unavailable, exactly as the contract requires.
3. **Its own slow schedule.** A dedicated coordinator polls every six hours, so a fragile external
   dependency can never slow down or block the one-minute health refresh.
4. **No install support in v1.** The entity declares no supported features and no auto-update, so
   Home Assistant offers no action that this integration cannot honor across Docker, Kubernetes and
   Helm deployments.
5. **Release URLs are built only from safe versions.** A latest version is interpolated into the
   upstream release URL only after matching a strict version pattern; development builds and any
   unexpected text yield no URL at all.
6. **Version fallback stays consistent.** `yes` carries no versions, so the installed version comes
   from the validated connection and the latest version mirrors it, which keeps the entity off
   rather than reporting an unknown latest version.

## Failure modes and rollback

- GitHub is unreachable — the check fails, the entity is unavailable and recovers on the next
  six-hour cycle.
- The deployment is too old for `/api/uptodate` — the capability probe already reports it as
  unsupported and no entity is created.
- Windmill returns unparseable text — the client raises a protocol error rather than inventing a
  version.
- A Cloud tenant uses a custom domain — the host check cannot detect it, but the opt-in default of
  disabled means the entity still requires a deliberate user decision.
- Rollback is one ticket commit; the entity is additive and its unique ID is derived from the entry.

## Security and privacy review

- Credentials: the update check is public and deliberately unauthenticated.
- Sensitive payloads: only two bounded version strings are retained.
- Permissions: none beyond reachability.
- Network exposure: one bounded GET every six hours, plus an outbound GitHub call performed by
  Windmill itself, never by Home Assistant.

## Open questions

  not an upstream guarantee, and ADR-0001 already names this as a revisit trigger.
