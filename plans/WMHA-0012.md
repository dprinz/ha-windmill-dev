# Plan for WMHA-0012

## Current state verified

- There is no `diagnostics.py` and no issue-registry use anywhere in `custom_components/windmill/`.
- Reauth already exists: `config_flow.py:271` has `async_step_reauth` and `async_step_reauth_confirm`,
  and every coordinator raises `ConfigEntryAuthFailed` on `WindmillAuthenticationError`. What is
  missing is proof that a reauth does not drop the user's options.
- Log throttling for repeated failures is already Home Assistant behavior:
  `DataUpdateCoordinator._async_refresh` logs the first failure at error level and every following
  one at debug level until a refresh succeeds. No integration code is needed; the ticket needs
  evidence, not a new mechanism.
- Nothing reacts to `WindmillRateLimitError.retry_after`. Every coordinator keeps polling at its
  fixed interval while Windmill is rate limiting, which is the "repeated failures spam API requests"
  half of the acceptance criterion.
- The capability matrix already distinguishes `unauthorized` (permission) from `unsupported`
  (version or deployment) and from `temporarily_unavailable` (transient), so repairs can be derived
  from it without inventing a version floor.
- `WindmillWorkerSnapshot.groups[group].versions` is the distinct-version count per worker group.

## Proposed changes

## Failure modes and rollback

- Diagnostics leaking a secret — mitigated by building the payload from an explicit allowlist of
  fields rather than dumping objects, and by a test that asserts the token string appears nowhere in
  the serialized output.
- Repair noise during a rolling Windmill upgrade — mitigated by the version-drift grace period and
  by deriving permission issues only from `unauthorized`, never from `temporarily_unavailable`.
- Backoff never recovering — the interval is restored on the first successful refresh and is bounded
  by a maximum.

## Security and privacy review

- Credentials: the token is never read into the diagnostics payload; the base URL is redacted
  entirely, so no URL — credential-bearing or not — survives a download.
- Sensitive payloads: no job arguments, results, logs, stack traces, worker IPs or worker-group
  config. Runnable paths are already visible in entity state and stay.
- Permissions: unchanged; no new endpoint is called.
- Network exposure: backoff only reduces request frequency.

## Open questions

- "Unsupported version" is expressed as a capability that is `unsupported` while the user enabled
  the feature, rather than as a hard version floor. A floor would be a new durable decision without
  evidence; the capability probe is the evidence the integration actually has.

## Plan changes

- The base URL is redacted rather than reduced to scheme and host. `normalize_base_url` already
  rejects credentials in a stored URL, so the remaining risk is the private hostname, and redacting
  is both simpler and stronger than reducing.
- The plan expected only backoff in `coordinator.py`. Applying it to all six coordinators without
  repeating the logic required a shared `WindmillCoordinator` base and renaming each
  `_async_update_data` to `_async_observe`. That is a wider diff than planned, but the alternative
  was six copies of the same `except` handling.
- Adding the issue listener to the capability coordinator activates its previously dormant six-hour
  refresh. Recorded in the ticket as a deliberate behavior change rather than hidden in the diff.
