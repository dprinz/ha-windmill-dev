# Plan for WMHA-0017

## Current state verified

- `WindmillRunCoordinator._observe` (`custom_components/windmill/coordinator.py:434`) aggregates
  every visible top-level job; there is no scope option yet.
- Retention lives in `RunObservationState` (watermark, `seen` deque of 200 job ids, monotonic
  `last_success`/`last_failure`, `initialized`) and is persisted per entry via `async_run_store`.
  The first poll after setup suppresses events (`initialized` guard), and completions at or below
  the watermark never fire again. This model already prevents replay; a scope change must reuse it,
  not bypass it.
- The runnable selection of WMHA-0008 is stored in `entry.options[OPT_RUNNABLES]` and parsed by
  `load_selections` into `RunnableSelection` values with a `(kind, path)` key. `WindmillJob.kind`
  uses the same `script`/`flow` vocabulary (`api.py`).
- The Home Assistant-started registry of WMHA-0009/0010 (`StartedJobRegistry`) is created in
  `__init__.py` after the run coordinator; it must move before it so the coordinator can consult it.
- The features step (onboarding) and the features options step share `_feature_schema`
  (`config_flow.py:141`); existing tests assert the exact schema defaults and stored options, so
  they must be extended, not bypassed.
- Translation parity between `strings.json`, `translations/en.json` and `translations/de.json` is
  enforced by `scripts/validate_repository.py`.

## Scope-change semantics (design decision)

A scope change is an options change and therefore reloads the entry (`OptionsFlowWithReload`). The
persisted retention state is deliberately kept across the change:

- `watermark`, `seen` and `initialized` are retained. Anything already observed, or completed at or
  below the watermark, can never fire again — no replay, no double publication, and the
  WMHA-0022/WMHA-0023 guards (publish only fresh snapshots, only after a successful poll) stay
  untouched because the event entity and snapshot flow do not change.
- `last_success` and `last_failure` are reset when the stored scope differs from the configured
  scope, so the last-run sensors describe completions of the selected scope only. The stored scope
  is persisted inside the existing run store (additive field, storage version stays 1; a missing
  scope means the legacy `all` behavior).
- A completion that happened shortly before the change but was never observed (above the watermark)
  may fire once under the new scope. That is the WMHA-0007 "newly observed" semantics, not a
  replay of historical jobs.
- Aggregate counters (`running`, `queued`) are computed per poll from the filtered window, so they
  respect the scope immediately after the reload.

Filtering happens in `WindmillRunCoordinator._observe` on the already-parsed, bounded
`WindmillJob` projection (`id`, `state`, `kind`, `path`, timestamps, `duration_ms`). No new field
is fetched or retained:

- `all` (default): current behavior, no filter.
- `selected_runnables`: keep jobs whose `(kind, path)` matches a stored selection key.
- `home_assistant_started`: keep jobs whose id is in the started-job registry.

## Failure modes and rollback

- Scope stored with an unknown value (manual storage edit) — `run_scope_from_options` falls back
  to `all`.
- `selected_runnables` scope without any selection — nothing matches; counters show zero and no
  events fire. Safe, documented in the field description.
- A tracked job is forgotten from the registry right after its completion event fires
  (WMHA-0019/0022 flow) — it was already remembered in retention during that poll, so filtering it
  out afterwards cannot duplicate or lose the event.
- Rollback: revert the diff; the stored `scope` field is ignored by the previous code, so a
  downgrade is safe.

## Security and privacy review
