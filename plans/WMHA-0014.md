# Plan for WMHA-0014

## Current state verified

- `custom_components/windmill/manifest.json` (version 0.1.0) lacks `issue_tracker`, which HACS
  requires (research R-002). All other required manifest keys are present.
- Repository layout (`custom_components/windmill/` as the single integration, root `README.md`)
  already matches the HACS integration requirements (R-002).
- No `hacs.json`, no `brand/` assets, no release or validation workflow exists.
- CI convention (`.github/workflows/repository-guardrails.yml`): actions pinned by major-version
  tag (`actions/checkout@v4`, `actions/setup-python@v5`), top-level `permissions:` set
  explicitly, triggers limited to `pull_request` and `push` to `main`.
- HACS extracts a `zip_release` asset directly into `custom_components/<domain>/`, so the ZIP
  must contain the integration files at its root (research R-006).
- `hacs/action` is a Docker action whose validator image (`ghcr.io/hacs/action:main`) floats
  regardless of the pinned ref (research R-005); `home-assistant/actions/hassfest` is only
  maintained on `master` (research R-008).
- Pillow 12.2.0 is available in `.venv` (transitive via Home Assistant), so a simple brand icon
  can be generated locally.

## Failure modes and rollback

- HACS action fails in CI on a check this plan did not anticipate (e.g. GitHub-side repo
  description/topics are not settable from a PR) — inspect the run log, add repo metadata or a
  documented `ignore` entry; rollback is deleting the workflow.
- hassfest flags manifest ordering or a missing key — fix manifest; no runtime impact.
- Release workflow fires on an unintended tag — tags are human-created and the check
  `tag == manifest version` plus the `v*` filter stop bad builds; the release is a draft and
  can simply be discarded.
- Generated icon is judged unfit — replace `brand/icon.png`; no code impact.

## Security and privacy review

- Credentials: none added; workflows use the default `GITHUB_TOKEN` only. No PAT, no secrets.
- Sensitive payloads: the ZIP contains only tracked integration source; the build runs from a
  clean checkout of the pushed tag.
- Permissions: validation workflow `permissions: {}` (HACS job) and `contents: read`
  (hassfest job); release workflow `contents: write` scoped to the single release job,
  triggered only by tag pushes (tags on this repository can only be pushed by users with
  write access — fork PRs cannot trigger it). No `pull_request_target`, no checkout of PR
  content in a write context.
- Third-party actions: pinned by full commit SHA with a comment naming the resolved version
  and date; the HACS action's floating Docker image is documented in research R-005.
- Network exposure: workflows download only the pinned actions and push only to this
  repository's own releases.

## Plan changes

Record material deviations and why they were necessary.

- 2026-08-02 — hassfest was run locally via Docker
  (`ghcr.io/home-assistant/hassfest`) and failed on a pre-existing defect:
  `strings.json` and `translations/en.json`/`de.json` contained a literal URL in
  `config.step.user.data_description.base_url`, which hassfest rejects. Fixed in
  place with the core-standard description-placeholder pattern (`{cloud_url}`
  plus `description_placeholders` in `config_flow.py::async_step_user`),
  because the ticket's own deliverable — the hassfest CI job — cannot pass
  otherwise. The remaining `[CONFIG_SCHEMA]` warning was deliberately left
  unfixed (it does not fail hassfest) and became backlog ticket WMHA-0024.
- 2026-08-02 — The HACS job lost its `actions/checkout` step: the upstream
  example workflow has none because the action validates through the GitHub
  API, and dropping it keeps `permissions: {}` meaningful.
- 2026-08-02 — GitHub repository metadata check (`gh api`) showed no
  description and no topics on the repository; the HACS action's `description`
  and `topics` checks would fail in CI. Not fixed by automation (GitHub-side
  setting, maintainer action); documented as a one-time step in
  `docs/development/versioning-and-releases.md`.
